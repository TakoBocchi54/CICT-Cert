# Backend database

Run backend commands from `backend/`, where `.env` supplies `DATABASE_URL`.

`sql/schema.sql` creates a **new, empty database**. Do not run it over an existing database.

For a database using the previous schema, back it up and stop the backend before running the one-time migration:

```powershell
node scripts/migrateSeminarSchema.js "Asia/Kuala_Lumpur"
```

The argument must be the timezone originally used for that database's `TIMESTAMP` values. `Asia/Kuala_Lumpur` is the inspected local database setting; confirm the original setting separately for Supabase. The script applies migrations `001` through `004` in order. Each migration uses a transaction. Migration `001` stops if certificate/blockchain history exists, email normalization produces duplicates, or existing data violates a constraint. Existing certificate history needs a reviewed backfill; the migration never invents student consent.

If migration `001` was already applied, use your database SQL client to apply only the remaining migrations in order: `002_remove_replacement_link.sql`, `003_remove_failure_reason.sql`, then `004_remove_certificate_created_at.sql`. These remove the optional replacement link, failure explanation, and certificate preparation timestamp respectively, preserving the certificate and transaction rows. Do not rerun the initial migration script on an already migrated database.

Deploy the migrated schema, backend, and frontend together: student responses now use `fullName`, and the old student `firstName`/`lastName` columns are removed. Faculty names are unchanged. Preserve a backup if the original name split is needed later.

## Seminar and certificate records

- `seminar` stores the title, date, faculty `createdBy`, and creation time.
- `seminar_registration` joins students to seminars. Its composite primary key prevents duplicate registration; `attended` defaults to false and is set by the final attendance import.
- Student Google email stays in `users.email`, normalized to lowercase without surrounding spaces. Registration references the student, so it needs no duplicate email, section, or school student number.
- Certificates reference a registration and keep recipient/seminar snapshots. Missing wallets, hashes, authorization, and consent are allowed while pending.
- Certificates keep `issuedAt` for successful issuance and `revokedAt` for revocation, without a draft `createdAt`. Pending or failed certificates have no `issuedAt`. Other tables retain their creation timestamps.
- Certificate numbers are generated by a sequence. They are unique and numeric; gaps are normal after failed inserts. Never calculate them with `MAX + 1`.
- Consent stores the exact message, signature, and timestamp for that certificate. Wallet-link consent is separate. Editing signed certificate facts requires clearing consent and obtaining a new approval.
- Issued certificate details cannot be edited. Revoke the original and issue a corrected certificate with a new certificate number. Both records remain, without a direct replacement link. One non-revoked certificate is allowed per registration; failed attempts retry the same record.
- Each blockchain attempt records `requestedBy` and a revocation reason for `REVOKE`. Failed attempts retain their `FAILED` status without a stored explanation. Only one pending attempt is allowed per certificate. Transaction hashes can be null before broadcast. Keep uncertain broadcasts pending until reconciled; a timeout alone does not prove failure.
- Event times use `TIMESTAMPTZ`; seminar dates use `DATE`. Hashes use lowercase `0x` plus 64 hex characters; wallet uniqueness ignores hex letter case.

These are database safeguards. CSV import, signature verification for certificate consent, faculty issuance/revocation endpoints, chain receipt reconciliation, and PDF generation are separate implementation steps. The future issuing service must check attendance, faculty permission, the configured issuer, and the student's certificate-specific signature before sending a transaction.

The manual student script now takes a full name and explicit program:

```powershell
node scripts/createStudent.js student@example.com "Juan Dela Cruz" "BS Computer Science"
```

## Checks

```powershell
npm test
```

Route tests use mocked database responses and a local identity signing key. Schema tests use real PostgreSQL in temporary schemas, clean up those schemas, and refuse remote database targets. Set a local `DATABASE_URL` to run those integration tests; otherwise they report a skip. They exercise both fresh installation and migration from `sql/fixtures/legacy-schema.sql`, including rollback when old certificate history needs a backfill.
