# Backend database

Run backend commands from `backend/`, where `.env` supplies `DATABASE_URL`.

`sql/schema.sql` creates a **new, empty database**. Do not run it over an existing database.

For a database using the previous schema, back it up and stop the backend before running the one-time migration:

```powershell
node scripts/migrateSeminarSchema.js "Asia/Kuala_Lumpur"
```

The argument must be the timezone originally used for that database's `TIMESTAMP` values. `Asia/Kuala_Lumpur` is the inspected local database setting; confirm the original setting separately for Supabase. The script applies migrations `001` through `004` in order. Each migration uses a transaction. Migration `001` stops if certificate/blockchain history exists, email normalization produces duplicates, or existing data violates a constraint. Existing certificate history needs a reviewed backfill; the migration never invents student consent.

If migration `001` was already applied, use your database SQL client to apply only the remaining migrations in order: `002_remove_replacement_link.sql`, `003_remove_failure_reason.sql`, then `004_remove_certificate_created_at.sql`. These remove the optional replacement link, failure explanation, and certificate preparation timestamp respectively, preserving the certificate and transaction rows. Do not rerun the initial migration script on an already migrated database.

Deploy the migrated schema, backend, and frontend together: student responses now use `fullName`, and the old student `firstName`/`lastName` columns are removed. Faculty names are unchanged. Preserve a backup if the original name split is needed later.

## Seminar and certificate records

- `seminar` stores the title, date, faculty `createdBy`, and creation time.
- `seminar_registration` joins students to seminars. Its composite primary key prevents duplicate registration; `attended` defaults to false and is set by the final attendance import.
- Student Google email stays in `users.email`, normalized to lowercase without surrounding spaces. Registration references the student, so it needs no duplicate email, section, or school student number.
- Certificates reference a registration and keep recipient/seminar snapshots. Missing wallets, hashes, authorization, and consent are allowed while pending.
- Certificates keep `issuedAt` for successful issuance and `revokedAt` for revocation, without a draft `createdAt`. Pending or failed certificates have no `issuedAt`. Other tables retain their creation timestamps.
- Certificate numbers are generated by a sequence. They are unique and numeric; gaps are normal after failed inserts. Never calculate them with `MAX + 1`.
- Consent stores the exact message, signature, and timestamp for that certificate. Wallet-link consent is separate. Editing signed certificate facts requires clearing consent and obtaining a new approval.
- Issued certificate details cannot be edited. Revoke the original and issue a corrected certificate with a new certificate number. Both records remain, without a direct replacement link. One non-revoked certificate is allowed per registration; failed attempts retry the same record.
- Each blockchain attempt records `requestedBy` and a revocation reason for `REVOKE`. Failed attempts retain their `FAILED` status without a stored explanation. Only one pending attempt is allowed per certificate. Transaction hashes can be null before broadcast. Keep uncertain broadcasts pending until reconciled; a timeout alone does not prove failure.
- Event times use `TIMESTAMPTZ`; seminar dates use `DATE`. Hashes use lowercase `0x` plus 64 hex characters; wallet uniqueness ignores hex letter case.

These are database safeguards. Signature verification for certificate consent, faculty issuance/revocation endpoints, chain receipt reconciliation, and PDF generation are separate implementation steps. The future issuing service must check attendance, faculty permission, the configured issuer, and the student's certificate-specific signature before sending a transaction. Issuance must coordinate using the same seminar row lock as attendance imports so attendance cannot change during approval of a blockchain attempt.

## Student accounts

Registering a student's Google account is what lets them sign in. Students are accounts, not per-seminar registrations: faculty manage them in the **Students** tab, with bulk CSV upload, an **Add one student** form, and a searchable list. Registration does not mark attendance or issue certificates.

The accepted CSV format is:

```csv
full_name,section,program,google_account
Juan Dela Cruz,CS 3-1,BS Computer Science,juan.delacruz@gmail.com
```

Only `full_name`, `program`, and `google_account` are required and stored. Section and other extra columns are ignored. Headers ignore surrounding spaces and letter case. Imports accept UTF-8 CSVs up to 1 MB, including quoted commas, escaped quotes, and a BOM. JSON rows (`POST /api/faculty/students`, 1–500 rows) get the same per-row checks (`readStudentRows` in `utils/seminarCsv.js`).

Emails are trimmed and lowercased; Gmail plus tags and dots are preserved, and Google Workspace email domains are accepted. Identical repeated emails are counted once; conflicting names/programs for the same email within one request reject it. Existing student names, programs and wallets are never changed, and re-registering an existing account is a no-op.

All rows are validated before writing, and each request is one transaction (`registerStudents` in `services/students.js`). A faculty email or an existing student account with no student profile rejects the whole batch, including newly inserted accounts. No real student records are seeded by the tests.

**Removing a student** (`DELETE`, requires `canIssue`) is only allowed when the account never linked a wallet (so the student never finished signing in) and has no certificate in any status. It deletes the student's attendance rows, student row and user row in one transaction, with the student row locked so a concurrent wallet link or certificate waits. The list's `removable` flag shows which rows qualify.

Faculty-only endpoints (session cookie of an active faculty account required):

Both student registration endpoints return `{ created, existing, duplicatesSkipped, students }`. `createdBy` on a seminar is always taken from the signed-in faculty account. Seminars are shared across CICT faculty; issuance and revocation require `canIssue`.

## Final attendance

In the seminar's **Attendance** step, choose a CSV, review the matches, then **Confirm attendance**. Only the `google_account` header is required. `full_name` and `program`, when present, are used only to prefill registration of attendees who don't have an account yet. Other columns are ignored:

```csv
full_name,section,program,student_id,google_account
Juan Dela Cruz,CS 3-1,BS Computer Science,1234567,juan.delacruz@gmail.com
```

- Attendance matches the normalized email against **all student accounts**. Names and school student IDs are never used for matching. Attendance import never creates accounts and never changes profile names, programs, or wallets.
- The preview returns `matched`, `unregistered` (each with `fullName`/`program` hints from the CSV and up to 3 `suggestions`), `facultyEmails` (cannot become students), `removed`, `blocked` and `canSave`. Suggestions are existing students with the same part before `@` (which also catches domain typos such as `gmial.com`) or the same normalized name as the CSV hint. They only help a human decide; nothing is matched automatically.
- `aliases` lets faculty say "this listed email is that existing student" after reviewing a suggestion. An alias key must be a listed email without its own account, and its target must be an existing student; otherwise the request fails with 409 and a fresh review is needed. Matched rows show `listedAs` for aliased emails.
- Unregistered or faculty emails block the whole save. The portal offers to register the unregistered ones (`POST /api/faculty/students`) and then reviews again. Duplicate emails count once. There is no attendance-percentage or eligibility calculation.
- A confirmed CSV is the **complete attendance list**. Confirming creates an attended `seminar_registration` row for each matched student (or marks the existing row attended) and marks this seminar's other rows absent. The review lists previously marked attendees whose attendance will be cleared. Empty/header-only CSVs are rejected to prevent accidentally clearing all attendance.
- Students without wallets may be marked attended; the preview and save response report how many still need wallet setup. No certificates or transactions are created by this step.
- A review does not save attendance. Confirmation resubmits that CSV, the same aliases and the server-provided `previewHash`. The hash covers the listed emails, aliases, matched student IDs, faculty emails and this seminar's rows. Changed CSV contents, a newly registered listed student, changed attendance, or relevant certificate/transaction states invalidate the old review with HTTP 409. Review again before saving.
- An issued certificate or unresolved blockchain attempt blocks clearing that recipient's attendance. A confirmed mint awaiting certificate reconciliation also blocks removal. Revoked certificate history remains intact.
- Saves are transactional and serialized per seminar. Repeating review and confirmation with the same final list changes nothing. Other seminars' attendance is preserved.

The manual student script now takes a full name and explicit program:

```powershell
node scripts/createStudent.js student@example.com "Juan Dela Cruz" "BS Computer Science"
```

## Pending certificates and recipient approval

After confirming final attendance, an authorized faculty account (`canIssue = true`) can select **Prepare pending certificates**. This reads `issuer()` from the configured Amoy contract and records its wallet in `issuer_wallet` if it is not already registered. An inactive issuer or a network mismatch blocks preparation. Only `AMOY_RPC_URL` and `CONTRACT_ADDRESS` are needed; no issuer private key is used by this step.

Preparation creates one pending certificate per attendee, assigns a numeric certificate number, and saves the recipient name, seminar title, and seminar date as certificate snapshots. Missing wallets are allowed. Repeat preparation preserves existing numbers, snapshots and approvals. It does not automatically create replacements for revoked certificates; use **Prepare replacement** on the Revocations page instead.

Students see pending certificates under **Certificate approvals** on their dashboard and collection. They open a review showing the certificate, issuer and recipient wallets, and the issuer-only revocation rule. **Approve with my wallet** signs the exact displayed message. The wallet linked to the registered Google account must sign. Linking a wallet during login is separate from approving a certificate. Students who link a wallet later can review their existing pending certificate without getting a new certificate number. Issued certificates appear in the existing dashboard and collection.

| Method | Endpoint | Access / body |
| --- | --- | --- |
| GET | `/api/faculty/seminars/:seminarID/certificates` | Faculty |
| POST | `/api/faculty/seminars/:seminarID/certificates/prepare` | Faculty with `canIssue` |
| GET | `/api/student/certificates` | Student; own certificates and confirmed mint details only |
| POST | `/api/student/certificates/:certificateID/consent-request` | Student; own certificate |
| POST | `/api/student/certificates/:certificateID/consent` | Student; `{ "challenge": "<signed server request>", "signature": "0x..." }` |

The approval request is signed by the server, bound to the student, certificate and contract, and expires after 10 minutes. Approval rechecks attendance, the linked wallet and certificate facts before verifying the wallet signature. A retry with the same signed request is idempotent; another approval cannot overwrite saved evidence. Changed certificate facts require a fresh review. The message, signature and approval timestamp are saved, but approval alone leaves status `PENDING` and `issuedAt` null. No blockchain transaction is submitted by approval.

`utils/certificateConsent.js` defines the canonical certificate hash: Keccak-256 of the UTF-8 JSON object with fields in this exact order: `version` (number `1`), `chainId` (number), `contractAddress` (lowercase), `issuerAddress` (lowercase), `certificateNo` (decimal string), `recipient` (lowercase wallet address), `recipientName`, `seminarTitle`, `seminarDate` (`YYYY-MM-DD`), and `burnAuth` (`IssuerOnly`). Text is the stored snapshot, without further normalization. The hash represents these facts, not PDF file bytes. Issuance and metadata verification must reuse this encoding.

## Faculty issuance on Amoy

Apply `sql/migrations/005_signed_transaction.sql` to existing databases. Fresh `schema.sql` includes the nullable `blockchain_record.signedTransaction TEXT` column; the general migration script also applies migration 005. This addition preserves all accounts and certificate records. It stores a signed transaction, never the private key, so an interrupted request can resume exactly the same mint.

Set `ISSUER_PRIVATE_KEY` in **backend/.env** to the same dev issuer key used for the deployed contract. Keep it out of frontend variables and Git. Restart the backend after changing environment settings. Missing or mismatched keys disable new minting without preventing login or verification. The issuer wallet needs Amoy POL; there is no fixed balance assumed sufficient for every batch.

Faculty select **Review issuance**, then **Confirm issuance on Amoy**. Only attended recipients with a linked wallet and saved consent enter the batch. The backend independently rechecks those conditions, reconstructs the approval message, verifies its wallet signature and canonical hash, verifies the deployed issuer and chain, simulates the mint, and checks funds before signing. Transactions are processed one at a time. Leaving the page stops remaining requests, but an already submitted transaction may still finish.

| Method | Endpoint | Access |
| --- | --- | --- |
| POST | `/api/faculty/seminars/:seminarID/certificates/:certificateID/issue` | Faculty with current `canIssue`; issue or resume this certificate |
| POST | `/api/faculty/seminars/:seminarID/certificates/:certificateID/issuance/check` | Faculty with current `canIssue`; reconcile/resubmit an existing attempt, never sign a new one |

The signed payload and its transaction hash are committed **before broadcasting**. Uncertain send responses remain pending. **Check transaction** rechecks the receipt and, when absent, resubmits that same signed payload. Never mark an uncertain transaction failed just because a request timed out. A PostgreSQL lock and a check for any outstanding issuer transaction prevent another seminar or backend instance from allocating the same wallet nonce. Keep this wallet dedicated to backend issuance; external nonce replacements or fee bumps require manual reconciliation.

The API waits for the receipt's block to be behind the RPC's `finalized` block, checks its canonical block hash, receipt sender and contract, the ERC-5484 `Issued` event, and the certificate's on-chain verification result. Only then are the token ID, block number, transaction status and certificate `issuedAt` committed together. Finality follows the [Polygon finality documentation](https://docs.polygon.technology/pos/concepts/finality/finality). An RPC without the finalized block tag must be replaced with one supporting it; issuance remains pending rather than claiming success.

A finalized revert marks the attempt/certificate failed, preserving its number and approval for a later retry. A successful receipt without the expected event or matching hash stays unresolved for review. Certificates already issued are returned without another mint. Hashes present on Amoy without a matching local attempt are blocked for manual reconciliation rather than minted again. Faculty see token IDs and explorer links, and students see confirmed certificates in their portal.

### Optional auto-issuance (`AUTO_ISSUE=true`)

When enabled, `services/autoIssue.js` runs every 30 seconds and right after each student approval. It first reconciles pending mint attempts, then, if no issuer transaction is pending, issues approved certificates oldest first through the same `issueCertificate` path as the buttons. The issuing faculty member is the one who prepared the certificate (`certificate.authorizedBy`), and their `canIssue` is rechecked on every mint. Approval never mints inline. Reverted (`FAILED`) certificates are not retried automatically. Limits: mints are one at a time (each waits for finality), a sleeping host mints only once awakened, a missing POL balance leaves approvals waiting, and nothing reviews a certificate between the student's approval and minting. The faculty buttons stay available as a fallback.

Public `GET /api/certificates/verify/:certHash` requires no login and checks the configured Amoy contract. Alongside blockchain status, token ID, recipient and timestamps, it returns the on-chain `issuerAddress` and a `certificate` containing `recipientName`, `seminarTitle`, `seminarDate` and the numeric `certificateNo` as a string. These details are published only when the saved snapshot reproduces the on-chain hash using the same recipient wallet, issuer, contract and chain. Email, approval signatures and signed transactions are never included.

`detailsStatus` is `Verified` for matching details, `NotFound` for an unknown on-chain hash, `Missing` for a blockchain record without a local snapshot, `Mismatch` for conflicting facts, or `Unavailable` if lookup fails. Missing or unconfirmed details return `certificate: null` without changing the blockchain's status. RPC failure returns 503; the database cannot override a revocation. The public page shows these distinctions and asks verifiers to compare the displayed details with the certificate they received. It does not inspect an uploaded PDF; someone reusing a valid QR on an altered document is detected by that comparison.

Students can select **Download PDF** on their dashboard or collection, review the certificate, and download a PDF file directly. The export renders only `Certificate.jsx`, at a fixed high resolution so mobile and desktop produce the same result. It preserves the template's `1.414:1` aspect ratio on a page 297 mm wide (approximately 210.04 mm high), with no extra page margins or print dialog. The certificate fills the single PDF page, with the scannable QR beside the bottom-right logo and the full certificate hash along the bottom. The PDF contains no clickable links; scan the QR to open public verification. The design is embedded as an image, so its text is not selectable in the PDF. The QR encodes `/verify?id=<certificateHash>` on the frontend's current origin; it contains no student email or authentication token. Generate shared PDFs from the deployed portal, because a QR generated on localhost points back to localhost. Verification remains public and checks the current blockchain status even if the PDF was saved before revocation. No PDF files or QR images are uploaded to another service.

Frontend PDF and verification-link checks: run `node --test src/lib/certificatePdf.test.js src/lib/certificateVerificationUrl.test.js` from `frontend`.

## Faculty revocation on Amoy

Faculty look up a certificate by its numeric certificate number. Only an `ISSUED` certificate with a confirmed mint from the configured contract can be revoked, and a non-empty reason (up to 500 characters) is required. The reason is stored in PostgreSQL on the `REVOKE` blockchain record with `requestedBy`; the contract does not store text.

| Method | Endpoint | Access |
| --- | --- | --- |
| GET | `/api/faculty/certificates?q=&status=` | Faculty; Registry list of `ISSUED`/`REVOKED` certificates (optional `status=ISSUED|REVOKED`), newest issued first, first 200 matches. `q` searches recipient name, email and seminar title, or an exact certificate number (`#` optional) |
| GET | `/api/faculty/certificates/:certificateNo` | Faculty; certificate facts, token ID, mint transaction and latest revocation attempt |
| POST | `/api/faculty/certificates/:certificateNo/revoke` | Faculty with current `canIssue`; `{ "reason": "..." }`; revoke or resume |
| POST | `/api/faculty/certificates/:certificateNo/revocation/check` | Faculty with current `canIssue`; reconcile/resubmit the existing attempt, never sign a new one |
| POST | `/api/faculty/certificates/:certificateNo/replacement` | Faculty with current `canIssue`; `{ "recipientName", "seminarTitle", "seminarDate" }`; prepare a replacement for a revoked certificate |

Revocation uses the same safeguards as issuance: the seminar row lock, the shared issuer advisory lock and outstanding-transaction check (a pending mint blocks a revoke and vice versa), the on-chain `verify` precheck, simulation and balance check, and committing the signed payload before broadcast. The certificate becomes `REVOKED` with the chain's `revokedAt` only after the receipt is finalized, carries the matching `Revoked` event, and `verify` reports Revoked for the same token. A finalized revert marks only the attempt `FAILED`; the certificate stays `ISSUED` and may be retried. Uncertain broadcasts stay pending.

### Correction by replacement

Issued certificates are never edited. To correct one, revoke it, then select **Prepare replacement** on its card. Faculty enter the corrected recipient name, seminar title and seminar date (prefilled from the revoked certificate). These corrections are saved only on the new certificate; the student profile and seminar records are unchanged. The replacement is a new `PENDING` certificate with a new certificate number for the same registration, using the student's currently linked wallet. Preparing it sends no transaction.

A replacement requires the original to be `REVOKED`, the registration to still be marked attended, and no other non-revoked certificate for that registration (only one replacement at a time). The student then approves the replacement's exact facts in the portal, and faculty issue it through the normal seminar issuance flow. The revoked original and its transaction history remain; the lookup shows the replacement's number and status, without a stored replacement link.

## Certificate templates

Apply `sql/migrations/006_certificate_templates.sql` to existing databases (fresh `schema.sql` includes it; the general migration script also applies it). It adds `certificate_template`, `certificate_template_signature` and the nullable `seminar."templateID"` (`ON DELETE SET NULL`, so deleting a template moves its seminars back to the built-in design). Nothing existing changes.

A template is an uploaded background plus placed fields (`fields` JSONB: recipient name, seminar title, seminar date, certificate number, QR code and up to 3 signature images with optional printed name/title). It only changes how a certificate is drawn: the canonical certificate hash, the consent message and the contract are unchanged.

- **Images:** PNG or JPEG only, recognised from the file header (`src/utils/certificateTemplate.js`), never SVG. Backgrounds: up to 5 MB, at least 1000 px on the long side, and A4 or US Letter proportions (landscape or portrait, ±2%); the paper size is derived from the pixel size and sets the PDF page. Signatures: up to 1 MB, any proportions, at most 3 per template. Uploads are raw request bodies (`Content-Type: image/png|image/jpeg`).
- **Sharing and permissions:** all faculty can list and choose any template; only its creator or a `canIssue` faculty can edit, replace the image, add/remove signatures or delete it.
- **Locking:** once any certificate exists for a seminar using a template, the template returns 409 on every change. The change takes `FOR SHARE` on those seminars before checking, which serializes with certificate preparation (it locks the seminar row `FOR UPDATE`). A seminar's own design is locked with its title and date.
- **Public images:** `/verify` is public, so template and signature images are served without a session, with the stored type, `nosniff` and long caching (template URLs carry `?v=<updatedAt>`).
- Certificate responses (`GET /api/student/certificates`, the consent request, and verified `GET /api/certificates/verify/:certHash` details) include `template`: `null` or `{ templateID, width, height, fields, imageUrl, signatures: [{ signatureID, imageUrl }] }`.

| Method | Endpoint | Body |
| --- | --- | --- |
| GET | `/api/faculty/certificate-templates` | — (all templates with `seminarCount`, `locked`, `canEdit`; no image bytes) |
| POST | `/api/faculty/certificate-templates?name=` | background image; creates the template with default field positions |
| PATCH | `/api/faculty/certificate-templates/:templateID` | `{ "name": "...", "fields": { "text": {...}, "qr": {...}, "signatures": [...] } }` |
| PUT | `/api/faculty/certificate-templates/:templateID/image` | replacement background image |
| DELETE | `/api/faculty/certificate-templates/:templateID` | — |
| POST | `/api/faculty/certificate-templates/:templateID/signatures` | signature image; returns `{ signatureID, imageUrl }` |
| DELETE | `/api/faculty/certificate-templates/:templateID/signatures/:signatureID` | — (also removes its placement from `fields`) |
| GET | `/api/certificate-templates/:templateID/image` | — (public) |
| GET | `/api/certificate-templates/:templateID/signatures/:signatureID` | — (public) |

## Checks

```powershell
npm test
```

Account/session route tests use mocked database responses and a local identity signing key. Seminar/attendance, certificate preparation/approval and schema tests use real PostgreSQL in temporary schemas, clean up those schemas, and refuse remote database targets. Set a local `DATABASE_URL` to run those integration tests; otherwise they report a skip. They cover fresh installation, migration from `sql/fixtures/legacy-schema.sql`, CSV validation, account reuse, attendance matching, concurrent requests, stale reviews, certificate safeguards, and rollback on database failures. Certificate approval tests use generated test wallets and a local read-only JSON-RPC fixture; no Amoy transaction or POL is used.
