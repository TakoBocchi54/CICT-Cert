# Backend database

Run backend commands from `backend/`, where `.env` supplies `DATABASE_URL`.

`sql/schema.sql` creates a **new, empty database**. Do not run it over an existing database.

For a database using the previous schema, back it up and stop the backend before running the one-time migration:

```powershell
node scripts/migrateSeminarSchema.js "Asia/Kuala_Lumpur"
```

The argument must be the timezone originally used for that database's `TIMESTAMP` values. `Asia/Kuala_Lumpur` is the inspected local database setting; confirm the original setting separately for Supabase. The script applies migrations `001` through `013` in order. Each migration uses a transaction. Migration `007` (Merkle batches) belongs to a new contract deployment and stops if any wallet link exists; see [Merkle batch issuance](#merkle-batch-issuance-and-sparse-merkle-revocation-migration-007). Migration `001` stops if certificate/blockchain history exists, email normalization produces duplicates, or existing data violates a constraint. Existing certificate history needs a reviewed backfill; the migration never invents student consent.

If migration `001` was already applied, use your database SQL client to apply only the remaining migrations in order: `002_remove_replacement_link.sql`, `003_remove_failure_reason.sql`, then `004_remove_certificate_created_at.sql`. These remove the optional replacement link, failure explanation, and certificate preparation timestamp respectively, preserving the certificate and transaction rows. Do not rerun the initial migration script on an already migrated database.

Deploy the migrated schema, backend, and frontend together: student responses now use `fullName`, and the old student `firstName`/`lastName` columns are removed. Faculty names are unchanged. Preserve a backup if the original name split is needed later.

## Seminar and certificate records

- `seminar` stores the title, date, faculty `createdBy`, creation time, a display-only `venue` (required by the API for new seminars; NULL only on seminars created before migration 009), the random `registrationToken` behind its registration link, and `registrationClosesAt` (NULL = registration closed). See [Registration link](#registration-link-migration-009).
- `seminar_registration` joins students to seminars. Its composite primary key prevents duplicate registration; `attended` defaults to false and is set by faculty ticking attendance (or the final attendance import).
- Student Google email stays in `users.email`, normalized to lowercase without surrounding spaces. Registration references the student, so it needs no duplicate email, section, or school student number.
- Certificates reference a registration and keep recipient/seminar snapshots. Missing wallets, hashes and authorization are allowed while pending; a hash requires a wallet (`chk_certificate_hash_wallet`).
- Certificates keep `issuedAt` for successful issuance and `revokedAt` for revocation, without a draft `createdAt`. Pending or failed certificates have no `issuedAt`. Other tables retain their creation timestamps.
- Certificate numbers are generated by a sequence. They are unique and numeric; gaps are normal after failed inserts. Never calculate them with `MAX + 1`.
- People see them as `<seminar date>-<number>`, e.g. `20261118-0042` (`formatCertificateNo` in `src/utils/certificateNumber.js` and `frontend/src/lib/certificateNumber.js`), on the certificate, PDF, pages and messages. The date is the certificate's own `seminarDate` snapshot and the number is the global `certificateNo`, padded to 4 digits; it does not restart per date. That is display only: the column, the certificate hash (`String(certificateNo)`), the proof file, the API and URLs keep the plain integer, so issued certificates still verify. Responses that list certificate numbers include `seminarDate` for this, and audit log rows carry `certificateDates` (number to date) for the numbers they mention. The Registry search accepts `20261118-0042`, `#42`, `0042` or `42`.
- Consent is given once, when the student links a wallet: `student_wallet` stores the exact signed message (`consentMessage`), its signature (`consentSignature`) and `createdAt`. There is no per-certificate approval. Once a certificate's hash is set (its batch is being signed), its hashed facts cannot change until the hash is cleared again; a pre-issuance name correction clears it.
- Issued certificate details cannot be edited. Revoke the original and issue a corrected certificate with a new certificate number. Both records remain, without a direct replacement link. One non-revoked certificate is allowed per registration; failed attempts retry the same record.
- Each blockchain attempt records `requestedBy` and a revocation reason for `REVOKE`. Failed attempts retain their `FAILED` status without a stored explanation. Only one pending attempt is allowed per certificate. There is one `blockchain_record` row per certificate; the rows of one batch share its `transactionHash` (indexed, not unique), and the signed payload is stored on one row of the batch only. Transaction hashes can be null before broadcast. Keep uncertain broadcasts pending until reconciled; a timeout alone does not prove failure.
- Event times use `TIMESTAMPTZ`; seminar dates use `DATE`. Hashes use lowercase `0x` plus 64 hex characters; wallet uniqueness ignores hex letter case.

These are database safeguards. The issuing service additionally checks attendance, the linked wallet, faculty permission and the configured issuer before signing, and takes the same seminar row lock as attendance imports so attendance cannot change while a batch is being signed.

## Student accounts

Registering a student's Google account is what lets them sign in. Students are accounts, not per-seminar registrations: faculty manage them in the **Students** tab, with bulk CSV upload, an **Add one student** form, and a searchable list. Registration does not mark attendance or issue certificates.

The accepted CSV format is:

```csv
first_name,last_name,section,program,google_account,contact_number
Juan,Dela Cruz,CS 3-1,BS Computer Science,juan.delacruz@gmail.com,09171234567
```

The name comes from `first_name` and `last_name`, joined as `First Last` (both required in every row), or from a single `full_name` column instead; a CSV with both forms, or only one of the two parts, is rejected. Only the name, `program`, `google_account`, and `contact_number` (exactly 11 digits once spaces, dashes, dots and parentheses are removed) are required and stored. Section and other extra columns are ignored. Headers ignore surrounding spaces and letter case. Imports accept UTF-8 CSVs up to 1 MB, including quoted commas, escaped quotes, and a BOM. JSON rows (`POST /api/faculty/students`, 1–500 rows) get the same per-row checks (`readStudentRows` in `utils/seminarCsv.js`).

Emails are trimmed and lowercased; Gmail plus tags and dots are preserved, and Google Workspace email domains are accepted. Identical repeated emails are counted once; conflicting names/programs for the same email within one request reject it. Existing student names, programs and wallets are never changed, and re-registering an existing account is a no-op.

All rows are validated before writing, and each request is one transaction (`registerStudents` in `services/students.js`). A faculty email or an existing student account with no student profile rejects the whole batch, including newly inserted accounts. No real student records are seeded by the tests.

**Removing a student** (`DELETE`, requires `canIssue`) is only allowed when the account never linked a wallet (so the student never finished signing in) and has no certificate in any status. It deletes the student's attendance rows, student row and user row in one transaction, with the student row locked so a concurrent wallet link or certificate waits. The list's `removable` flag shows which rows qualify.

## Registration link (migration 009)

Students register for a seminar themselves through the link faculty share, `<frontend origin>/register/<registrationToken>`. The token is a random UUID so seminars can't be found by guessing IDs. Registration is open while `now() < "registrationClosesAt"`; nothing runs at the deadline. Closing early sets the deadline to now, and editing the deadline (before certificates exist) reopens it. Existing seminars get a token and a NULL deadline, so their registration stays closed. Apply `sql/migrations/009_seminar_registration_link.sql` (the general migration script applies it too).

Public endpoints (`routes/registration.js`):

| Method | Endpoint | Body |
| --- | --- | --- |
| GET | `/api/register/:token` | — returns title, date, venue, `registrationClosesAt`, `open`. With an optional `Authorization: Bearer <Web3Auth ID token>` also returns `email`, `account` (`{ fullName, program, contactNumber }` or null) and `registered`. 404 for an unknown token, 401 for a bad ID token, 403 for a faculty account |
| POST | `/api/register/:token` | `{ "fullName": "...", "program": "...", "contactNumber": "0917 123 4567" }` with the Bearer ID token (required). The contact number is stored without spaces, dashes, dots or parentheses and must then be exactly 11 digits. Rate-limited |

POST runs in one transaction holding a `FOR SHARE` lock on the seminar row (registrations run in parallel but wait for closing, editing or preparing). It returns 409 when registration is closed, creates the student account when missing, otherwise **saves the edited name, program and contact number** on the existing account, then adds an unattended `seminar_registration` row and starts the student session. Registering again returns 200 with `alreadyRegistered: true`; a new registration returns 201. Already-prepared certificates keep their name snapshot; faculty review names before issuing.

This is the only way, besides faculty, that a student account is created. The login page still answers 403 for a Google account that never registered. Any Google account with the link can register, so faculty remove registrants who aren't CICT students; only students faculty mark as attended receive certificates. No student number or section is collected. The contact number (`student."contactNumber"`, migration 011) is collected on the link page and on the Students tab's single-student form (required, 11 digits, on every faculty path including the bulk CSV import). An existing account is never updated by faculty registration, only by the student through a link. Apply `sql/migrations/011_student_contact_number.sql` to existing databases (the general migration script applies it too).

## Final attendance

In the seminar's **Attendance** step, choose a CSV, review the matches, then **Confirm attendance**. Only the `google_account` header is required. `full_name` (or `first_name` and `last_name`, joined) and `program`, when present, are used only to prefill registration of attendees who don't have an account yet. Other columns are ignored:

```csv
full_name,section,program,student_id,google_account
Juan Dela Cruz,CS 3-1,BS Computer Science,1234567,juan.delacruz@gmail.com
```

- Attendance matches the normalized email against **all student accounts**. Names and school student IDs are never used for matching. Attendance import never creates accounts and never changes profile names, programs, or wallets.
- The preview returns `matched`, `unregistered` (each with `fullName`/`program` hints from the CSV and up to 3 `suggestions`), `facultyEmails` (cannot become students), `removed`, `blocked` and `canSave`. Suggestions are existing students with the same part before `@` (which also catches domain typos such as `gmial.com`) or the same normalized name as the CSV hint. They only help a human decide; nothing is matched automatically.
- `aliases` lets faculty say "this listed email is that existing student" after reviewing a suggestion. An alias key must be a listed email without its own account, and its target must be an existing student; otherwise the request fails with 409 and a fresh review is needed. Matched rows show `listedAs` for aliased emails.
- Unregistered or faculty emails block the whole save. The portal offers to register the unregistered ones (`POST /api/faculty/students`) and then reviews again. Duplicate emails count once. There is no attendance-percentage or eligibility calculation.
- A confirmed CSV is the **complete attendance list**. Confirming creates an attended `seminar_registration` row for each matched student (or marks the existing row attended) and marks this seminar's other rows absent. The review lists previously marked attendees whose attendance will be cleared. Empty/header-only CSVs are rejected to prevent accidentally clearing all attendance.
- Students without wallets may be marked attended; the preview and save response report how many still need wallet setup. No certificates or transactions are created by this step.
- A review does not save attendance. Confirmation resubmits that CSV, the same aliases and the server-provided `previewHash`. The hash covers the listed emails, aliases, matched student IDs, faculty emails and this seminar's rows. Changed CSV contents, a newly registered listed student, changed attendance, or relevant certificate/transaction states invalidate the old review with HTTP 409. Review again before saving.
- An issued certificate or unresolved blockchain attempt blocks clearing that recipient's attendance. A confirmed mint awaiting certificate reconciliation also blocks removal. Revoked certificate history remains intact.
- Saves are transactional and serialized per seminar. Repeating review and confirmation with the same final list changes nothing. Other seminars' attendance is preserved.

The manual student script now takes a full name and explicit program:

```powershell
node scripts/createStudent.js student@example.com "Juan Dela Cruz" "BS Computer Science"
```

## Pending certificates and name review

After confirming final attendance, an authorized faculty account (`canIssue = true`) can select **Prepare certificates** (confirming attendance also prepares them). This reads `issuer()` from the configured Amoy contract and records its wallet in `issuer_wallet` if it is not already registered. An inactive issuer or a network mismatch blocks preparation. Only `AMOY_RPC_URL` and `CONTRACT_ADDRESS` are needed; no issuer private key is used by this step.

Preparation creates one pending certificate per attendee, assigns a numeric certificate number, and saves the recipient name, seminar title, and seminar date as certificate snapshots. Missing wallets are allowed. Repeat preparation preserves existing numbers and snapshots. It does not automatically create replacements for revoked certificates; use **Prepare replacement** on the Revocations page instead.

The seminar's **Review** step lists every certificate with the name exactly as it will be printed, the student's email and wallet status. Faculty with `canIssue` can **Correct name** on a `PENDING`/`FAILED` certificate that is not in a pending transaction. This changes only the certificate's snapshot (not the student's account name) and clears its hash; issuance computes it again. Students see a certificate only once it is issued (the Upcoming certificates card was removed on 16 November). Students do not sign anything per certificate: the wallet-link signature at first sign-in is their standing consent.

`utils/certificateConsent.js` defines the canonical certificate hash: Keccak-256 of the UTF-8 JSON object with fields in this exact order: `version` (number `2`), `chainId` (number), `contractAddress` (lowercase), `issuerAddress` (lowercase), `certificateNo` (decimal string), `recipient` (lowercase wallet address), `recipientName`, `seminarTitle`, `seminarDate` (`YYYY-MM-DD`), and `burnAuth` (`Neither`: nobody can burn the token). Text is the stored snapshot, without further normalization. The hash represents these facts, not PDF file bytes. Issuance, the proof file and verification reuse this encoding. The same file builds the wallet-link consent message.

## Merkle batch issuance and sparse Merkle revocation (migration 007)

The contract (`smart_contract/contracts/CICTCertificate.sol`) still mints one ERC-5484 soulbound token per certificate, but issues a whole batch in one transaction and revokes many certificates in one transaction:

- **Batch root.** `issueBatch(seminarId, root, recipients, certHashes)` stores an immutable Merkle root under a new batch ID linked to the seminar and mints one token per recipient. Each token stores only its batch ID. Leaf = `keccak256(abi.encode(uint256 index, bytes32 certificateHash))` with `index = tokenId - firstTokenId`; leaves are in certificate-number order and pairs are hashed in sorted order (OpenZeppelin `MerkleProof`). The `BatchIssued` event carries the batch's hashes, so every tree can be rebuilt from the chain.
- **Revocation root.** One sparse Merkle tree of depth 64 keyed by token ID (leaf `1` = revoked, `0` = not). `revokeBatch(newRoot, tokenIds)` replaces the single on-chain `revocationRoot` and logs the token IDs. Tokens are never burned.
- **Verification.** `verify(tokenId, certificateHash, merkleProof, smtBitmap, smtSiblings)` checks inclusion against the token's batch root and the revocation proof against the current root, and returns `Valid`, `Revoked` or `NotFound` (bad proofs revert). The compressed SMT proof sends only non-empty siblings plus a 64-bit bitmap.
- `utils/merkle.js` builds both trees with `viem` only. Trees are rebuilt from the database on each use (no stored nodes).

Gas measured in `smart_contract/test/GasBenchmark.ts` (unoptimized compiler, batch of 100): one transaction per certificate with a stored hash costs 100,805 gas per certificate; this contract 74,871 (26% less). Revoking 1,000 certificates: about 459k gas with the SMT versus 8.5M by burning or 22.8M with a per-token mapping. Run `npx hardhat test mocha` in `smart_contract` to reprint the tables.

**Upgrading an existing database.** Migration 007 adds `consentMessage`/`consentSignature` to `student_wallet`, removes the per-certificate consent columns, makes `blockchain_record.transactionHash` non-unique and replaces the consent branch of the certificate trigger. Certificates from the old contract cannot be verified on the new one, so this is a reset: back up, deploy the contract (`npx hardhat run scripts/deploy.ts --network amoy` in `smart_contract`, spends Amoy POL), set `CONTRACT_ADDRESS`, run `node scripts/resetTestData.js --yes` (keeps faculty accounts), run the migration, and restart. Deploy first: the reset script refuses a `CONTRACT_ADDRESS` that has already issued a batch, because the chain's revocation root would no longer match the emptied database and every verification and revocation would fail. Students link their wallet again at next sign-in, which records their consent.

## INTEGER IDs (migration 008)

Every ID, `certificateNo` (and its sequence), `blockchain_record."tokenID"` and `"blockNum"` are `INTEGER` instead of `BIGINT`. Apply `sql/migrations/008_integer_ids.sql` to existing databases (the general migration script applies it too); it rolls back if any stored value is above 2147483647. Route ID validators reject values above that limit with 400. Because `pg` returns `INTEGER` as a JavaScript number, JSON responses now carry IDs as numbers; the public verification `tokenId` and the proof file's `tokenId`/`blockNumber` stay strings. The certificate hash is unchanged because it already encodes `String(certificateNo)`.

## Faculty issuance on Amoy

Apply `sql/migrations/005_signed_transaction.sql` to existing databases. Fresh `schema.sql` includes the nullable `blockchain_record.signedTransaction TEXT` column; the general migration script also applies migration 005. It stores a signed transaction, never the private key, so an interrupted request can resume exactly the same transaction.

Set `ISSUER_PRIVATE_KEY` in **backend/.env** to the same dev issuer key used for the deployed contract. Keep it out of frontend variables and Git. Restart the backend after changing environment settings. Missing or mismatched keys disable new minting without preventing login or verification. The issuer wallet needs Amoy POL; there is no fixed balance assumed sufficient for every batch.

In the seminar's **Issue** step, faculty select **Issue N certificates**, then **Confirm issuance on Amoy**. Every attended certificate with a linked wallet (`PENDING` or `FAILED`) enters the batch, in certificate-number order, up to `ISSUE_BATCH_SIZE` per transaction (default `100`, allowed `1` to `200`; about 7.5M gas at 100). Each transaction is its own batch with its own root. The portal sends the next batch after the previous one is final, while `remaining > 0`. Certificates that cannot be issued are returned in `skipped` with a reason (attendance not confirmed, no wallet yet, prepared for a different issuer wallet). A seminar may get later batches for late wallets and replacements. Leaving the page stops remaining batches, but an already submitted transaction may still finish.

| Method | Endpoint | Access |
| --- | --- | --- |
| POST | `/api/faculty/seminars/:seminarID/certificates/issue` | Faculty with current `canIssue`; sign and send the seminar's next batch, or resume its pending one |
| POST | `/api/faculty/seminars/:seminarID/certificates/issuance/check` | Faculty with current `canIssue`; reconcile/resubmit the pending batch, never sign a new one |

Both return `{ transactionStatus, transactionHash, issued, remaining, skipped, batchId?, warning? }`. `transactionStatus` is `null` when nothing is pending, otherwise `PENDING`, `CONFIRMED` or `FAILED`.

The backend computes each certificate's hash and the batch root, simulates `issueBatch`, checks funds, and commits the signed payload, its hash and one `MINT` row per certificate **before broadcasting**. Uncertain send responses remain pending. **Check transaction** rechecks the receipt and, when absent, resubmits that same signed payload (after confirming it still encodes the same batch). Never mark an uncertain transaction failed just because a request timed out. The seminar row lock, a PostgreSQL advisory lock on the issuer and a check for any outstanding issuer transaction prevent another seminar or backend instance from allocating the same wallet nonce. Keep this wallet dedicated to backend issuance; external nonce replacements or fee bumps require manual reconciliation.

The API waits for the receipt's block to be behind the RPC's `finalized` block and checks its canonical block hash, sender and contract. Success additionally requires a `BatchIssued` event matching the seminar, root and hashes, and an ERC-5484 `Issued` event to the right wallet for every token (token ID = `firstTokenId` + batch position). Only then are token IDs, block number, transaction status and certificate `issuedAt` (the block time) committed together. Finality follows the [Polygon finality documentation](https://docs.polygon.technology/pos/concepts/finality/finality). An RPC without the finalized block tag must be replaced with one supporting it; issuance remains pending rather than claiming success.

A finalized revert marks the whole batch's rows and certificates `FAILED`, preserving their numbers for a later batch. A successful receipt without the expected events stays unresolved for review. Faculty see token IDs and explorer links, and students see confirmed certificates in their portal. There is no auto-issuance: faculty review the list and issue.

Public `GET /api/certificates/verify/:certHash` requires no login. It finds the token and its batch in the database, rebuilds the inclusion proof and the revocation proof, and calls the contract's `verify`. If the on-chain revocation root matches neither the confirmed revocations nor confirmed plus the pending revocation batch, it answers 503 instead of guessing. The response is `{ status: "NotFound"|"Valid"|"Revoked", tokenId, batchId, recipient, issuedAt, revokedAt, issuerAddress, contractAddress, transactionHash, certificate, detailsStatus }`; `revokedAt` comes from the database and is `"0"` until the revocation is final there. `contractAddress` and `transactionHash` (the confirmed minting transaction, `null` when not found) are for the page's Polygonscan links, so a verifier can check the token, the transaction and both wallets there. `certificate` contains `certificateNo`, `recipientName`, `seminarTitle`, `seminarDate` and `template`, published only when the saved snapshot reproduces the hash using the on-chain recipient wallet, issuer, contract and chain. Email, consent signatures and signed transactions are never included.

`detailsStatus` is `Verified` for matching details, `NotFound` for an unknown hash, `Missing` for a blockchain record without a local snapshot, `Mismatch` for conflicting facts, or `Unavailable` if lookup fails. Missing or unconfirmed details return `certificate: null` without changing the blockchain's status. RPC failure returns 503; the database cannot override a revocation. The public page shows these distinctions and asks verifiers to compare the displayed details with the certificate they received. It does not inspect an uploaded PDF; someone reusing a valid QR on an altered document is detected by that comparison.

**Proof download.** On a certificate's page, students can select **Download Merkle proof (JSON)**. The file (`format: "cict-cert-merkle-proof-v1"`) holds the network and contract, the canonical certificate payload (its `keccak256` as written is `certificateHash`), `tokenId`, `index`, `leaf`, `merkleProof`, `merkleRoot`, the issuing transaction and block, and how to check it with the contract's `verify` or `batchOf(recordOf(tokenId).batchId).root`. It lets anyone check inclusion without this site; revocation status still comes from the current on-chain root.

Students can select **Download PDF** on their dashboard or collection, review the certificate, and download a PDF file directly. The export renders only `Certificate.jsx`, at a fixed high resolution so mobile and desktop produce the same result. It preserves the template's `1.414:1` aspect ratio on a page 297 mm wide (approximately 210.04 mm high), with no extra page margins or print dialog. The certificate fills the single PDF page, with the scannable QR beside the bottom-right logo and the full certificate hash along the bottom. The PDF contains no clickable links; scan the QR to open public verification. The design is embedded as an image, so its text is not selectable in the PDF. The QR encodes `/verify?id=<certificateHash>` on the frontend's current origin; it contains no student email or authentication token. Generate shared PDFs from the deployed portal, because a QR generated on localhost points back to localhost. Verification remains public and checks the current blockchain status even if the PDF was saved before revocation. No PDF files or QR images are uploaded to another service.

Frontend PDF and verification-link checks: run `node --test src/lib/certificatePdf.test.js src/lib/certificateVerificationUrl.test.js` from `frontend`.

## Faculty revocation on Amoy

Only an `ISSUED` certificate with a confirmed mint from the configured contract can be revoked, and a non-empty reason (up to 500 characters) is required. The reason is stored in PostgreSQL on each `REVOKE` blockchain record with `requestedBy`; the contract does not store text. In the **Registry**, faculty with `canIssue` tick issued certificates and select **Revoke N** with one reason: up to 200 certificates go in one `revokeBatch` transaction. A certificate's **Revoke/Details** page revokes one.

| Method | Endpoint | Access |
| --- | --- | --- |
| GET | `/api/faculty/certificates?q=&status=` | Faculty; Registry list of `ISSUED`/`REVOKED` certificates (optional `status=ISSUED|REVOKED`), newest issued first, first 200 matches. `q` searches recipient name, email and seminar title, or an exact certificate number (`#` optional) |
| GET | `/api/faculty/certificates/issuer-wallet` | Faculty; the contract's `issuer()` address and its Amoy POL balance (`{ address, balance }`, balance in POL as a decimal string); 503 when the RPC or contract settings fail |
| GET | `/api/faculty/certificates/:certificateNo` | Faculty; certificate facts, token ID, mint transaction and latest revocation attempt |
| POST | `/api/faculty/certificates/revoke` | Faculty with current `canIssue`; `{ "certificateNos": ["12", "15"], "reason": "..." }`; revoke in one transaction or resume the pending one |
| POST | `/api/faculty/certificates/revocation/check` | Faculty with current `canIssue`; `{ "certificateNos": [...] }`; reconcile/resubmit, never sign a new one |
| POST | `/api/faculty/certificates/:certificateNo/revoke` | Faculty with current `canIssue`; `{ "reason": "..." }`; the same for one certificate |
| POST | `/api/faculty/certificates/:certificateNo/revocation/check` | Faculty with current `canIssue`; the same for one certificate |
| POST | `/api/faculty/certificates/:certificateNo/replacement` | Faculty with current `canIssue`; `{ "recipientName", "seminarTitle", "seminarDate" }`; prepare a replacement for a revoked certificate |

The batch routes return `{ warning?, certificates: [{ certificateNo, status, revokedAt, tokenID, transactionStatus, transactionHash, reason }] }`; the single-certificate routes return one of those objects (plus `warning`).

Before signing, the backend requires the on-chain `revocationRoot` to equal the SMT root of the token IDs already `REVOKED` in the database (otherwise 409: database and chain disagree). The new root is that set plus this batch. Revocation uses the same safeguards as issuance: the affected seminar rows locked in ID order, the shared issuer advisory lock and outstanding-transaction check (a pending mint blocks a revoke and vice versa), simulation and balance check, and committing the signed payload before broadcast. Certificates become `REVOKED` with the block time as `revokedAt` only after the receipt is finalized and carries the matching `RevocationRootUpdated` event. A finalized revert marks only the attempts `FAILED`; the certificates stay `ISSUED` and may be retried. Uncertain broadcasts stay pending.

### Correction by replacement

Before issuance, correct a name in the seminar's Review step instead. Issued certificates are never edited. To correct one, revoke it, then select **Prepare replacement** on its card. Faculty enter the corrected recipient name, seminar title and seminar date (prefilled from the revoked certificate). These corrections are saved only on the new certificate; the student profile and seminar records are unchanged. The replacement is a new `PENDING` certificate with a new certificate number for the same registration, using the student's currently linked wallet. Preparing it sends no transaction.

A replacement requires the original to be `REVOKED`, the registration to still be marked attended, and no other non-revoked certificate for that registration (only one replacement at a time). Faculty issue it from the seminar's Issue step, where it goes out in a new batch with its own root. The revoked original and its transaction history remain; the lookup shows the replacement's number and status, without a stored replacement link.

## Certificate templates

Apply `sql/migrations/006_certificate_templates.sql` to existing databases (fresh `schema.sql` includes it; the general migration script also applies it). It adds `certificate_template`, `certificate_template_signature` and the nullable `seminar."templateID"` (`ON DELETE SET NULL`, so deleting a template moves its seminars back to the built-in design). Nothing existing changes.

A template is an uploaded background plus placed fields (`fields` JSONB: recipient name, seminar title, seminar date, certificate number, QR code and up to 3 signature images with optional printed name/title). It only changes how a certificate is drawn: the canonical certificate hash and the contract are unchanged.

- **Images:** PNG or JPEG only, recognised from the file header (`src/utils/certificateTemplate.js`), never SVG. Backgrounds: up to 5 MB, at least 1000 px on the long side, and A4 or US Letter proportions (landscape or portrait, ±2%); the paper size is derived from the pixel size and sets the PDF page. Signatures: up to 1 MB, any proportions, at most 3 per template. Uploads are raw request bodies (`Content-Type: image/png|image/jpeg`).
- **Sharing and permissions:** all faculty can list and choose any template; only its creator or a `canIssue` faculty can edit, replace the image, add/remove signatures or delete it.
- **Locking:** once any certificate exists for a seminar using a template, the template returns 409 on every change. The change takes `FOR SHARE` on those seminars before checking, which serializes with certificate preparation (it locks the seminar row `FOR UPDATE`). A seminar's own design is locked with its title and date.
- **Public images:** `/verify` is public, so template and signature images are served without a session, with the stored type, `nosniff` and long caching (template URLs carry `?v=<updatedAt>`).
- Certificate responses (`GET /api/student/certificates` and verified `GET /api/certificates/verify/:certHash` details) include `template`: `null` or `{ templateID, width, height, fields, imageUrl, signatures: [{ signatureID, imageUrl }] }`.

| Method | Endpoint | Body |
| --- | --- | --- |
| GET | `/api/faculty/certificate-templates` | — (all templates with `seminarCount`, `locked`, `canEdit`; no image bytes) |
| POST | `/api/faculty/certificate-templates?name=` | background image; creates the template with default field positions |
| PATCH | `/api/faculty/certificate-templates/:templateID` | `{ "name": "...", "fields": { "text": {...}, "qr": {...}, "signatures": [...] } }` |
| PUT | `/api/faculty/certificate-templates/:templateID/image` | replacement background image |
| DELETE | `/api/faculty/certificate-templates/:templateID` | — |
| POST | `/api/faculty/certificate-templates/:templateID/signatures` | signature image; returns `{ signatureID, imageUrl }` |
| DELETE | `/api/faculty/certificate-templates/:templateID/signatures/:signatureID` | — (also removes its placement from `fields`) |
| GET | `/api/certificate-templates/:templateID/image` | — (public) |
| GET | `/api/certificate-templates/:templateID/signatures/:signatureID` | — (public) |

## Notifications (migration 010)

In-app notifications have no events table. `GET /api/notifications` (student or faculty session, re-checked against the database) derives each account's items from timestamps the app already keeps, newest first, at most 20, from the last 60 days, and returns `{ unread, seenAt, items: [{ id, kind, text, at, link }] }`. `POST /api/notifications/seen` sets `users."notificationsSeenAt"`; items newer than it are unread.

| Kind | Who | From |
|---|---|---|
| `issued`, `revoked` | the student | `certificate."issuedAt"` / `"revokedAt"` (+ the confirmed revocation's reason) |
| `registrations` | all faculty | `seminar_registration."registeredAt"`, one item per seminar, counting those since the account last looked |
| `closed` | all faculty | `seminar."registrationClosesAt"` that has passed |
| `failed` | `canIssue` | a FAILED mint whose certificates are still unissued, or a FAILED revocation whose certificates are still issued |
| `pending` | `canIssue` | a transaction PENDING for more than 15 minutes |
| `low-balance` | `canIssue` | the issuer balance below `ISSUER_LOW_BALANCE_POL` (default 0.5 POL, about two full 100-certificate batches at 25–35 gwei); left out when the RPC fails |

`issuer_wallet."lowBalanceSince"` is set when the balance is first seen below the threshold (on the dashboard or in notifications) and cleared once it is above again, so the low-balance item keeps its time and a later drop is a new item. `GET /api/faculty/certificates/issuer-wallet` also returns `threshold` and `low`. There is no email or push; everything is in the app.

## Audit log (migration 012)

`audit_log` records every successful faculty change (POST/PATCH/PUT/DELETE under `/api/faculty/`), written by `middleware/auditLog.js`, which is mounted once in `app.js` and needs no change in the routes. It is written when the route sends its response, so a change is recorded even if the browser left first (for example during a slow issuance). Not recorded: `.../attendance/preview` (changes nothing) and the polled `.../issuance/check` and `.../revocation/check` (they only re-check a transaction whose issue or revoke is already recorded). A row holds the time, the actor's id, name and email at that moment (no foreign key, so history outlives the account), the action (`METHOD /route` with numeric ids replaced by `:id`, for example `POST /faculty/seminars/:id/certificates/issue`), the numeric ids from the URL, and `details`: only the fields that action uses (seminar fields for seminar create/edit, `attended`, `recipientName`, `certificateNos` and `reason` for revokes, the replacement's facts, a template's `name`), strings cut to 300 characters and lists to 200 items. CSVs, passwords, contact numbers and images are never stored. A trigger rejects UPDATE and DELETE; `scripts/resetTestData.js` deliberately leaves the table alone. Logins and student actions are not recorded.

`GET /api/faculty/audit-log` (`canIssue` only) returns rows newest first. `?limit` (1-100, default 50), `?before=<auditID>` continues after the last row of the previous page, `?q=` matches the actor's name or email or the action, and `?kind=` (`certificates`, `attendance`, `seminars`, `students`, `account`) keeps one group of actions (400 for any other value). Rows for `/faculty/members/:id` also carry `targetName`/`targetEmail`, the changed account's current name and email (NULL once it is gone), so the page names it instead of showing its internal ID. The page is the Audit log section of Account settings (`frontend/src/components/AuditLog.jsx`, `/faculty/account?section=audit`); faculty without `canIssue` see it greyed out, and the old `/faculty/audit-log` path redirects there.

shortcut: the row is written just after the response is sent, so a write failure or a crash at that instant loses one entry (the failure is logged). Move the insert into each route's transaction if the log must be lossless.

## Faculty accounts (migration 013)

Faculty with `canIssue` manage faculty accounts in Account settings → Faculty accounts (`frontend/src/components/FacultyMembers.jsx`), so organizers no longer need `scripts/createFaculty.js`. Accounts are never deleted (seminars, certificates, templates, blockchain records and the audit log point at them): `cict_faculty."deactivatedAt"` switches one off (NULL = active). A deactivated account can't sign in (the login answers the same "Invalid email or password" as a wrong password) and its open sessions stop working on their next request, because `requireActiveFaculty`, `/auth/me`, `/auth/faculty/me`, the notifications session check and the Account settings routes all require `"deactivatedAt" IS NULL`. `cict_faculty."temporaryPassword"` is true after an administrator generated the password and false once its owner changes it in Account settings, which shows a reminder meanwhile (a change is recommended, not forced).

| Method | Path | Body / result |
|---|---|---|
| GET | `/api/faculty/members` | — every faculty account, active first, without password hashes |
| POST | `/api/faculty/members` | `{ firstName, lastName, email, canIssue? }` (default `false`) → 201 `{ member, temporaryPassword }`; 409 when the email already has a faculty or student account |
| PATCH | `/api/faculty/members/:facultyID` | `{ canIssue?, active? }` → the updated account |
| POST | `/api/faculty/members/:facultyID/reset-password` | → `{ temporaryPassword }` |

All four require an active `canIssue` faculty session. The generated password is 16 characters in four groups, from an alphabet without look-alikes (about 92 bits); it is returned once, stored only as a bcrypt hash (cost 12) and never written to the audit log (only names, email, `canIssue` and `active` are). Nobody can remove their own issuing permission, deactivate themselves or reset their own password here (409); a PATCH locks the caller's and the target's rows and re-checks the caller inside the lock, so two administrators demoting each other at once can't leave nobody in charge. A password reset doesn't end sessions already open on the person's devices (they last up to 8 hours); deactivate the account to cut access at once.

Apply `sql/migrations/013_faculty_management.sql` to existing databases before deploying this backend: the login and session checks read the new columns.
